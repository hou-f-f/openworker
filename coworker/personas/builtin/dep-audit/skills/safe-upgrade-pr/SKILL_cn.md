---
[English](SKILL.md) · [简体中文](SKILL_cn.md)

将分诊后的安全通告转化为可以让代码审查者放心大胆合并的依赖升级 PR。

1. **按技术生态独立建分支**（如 `security/deps-npm`、`security/deps-python`），采取**最小化可行升级**策略：升级到包含修复的 patch/minor 次小版本，而不是盲目升到“最新版 (latest)”。涉及破坏性变更的大版本（Major）必须单独设立分支并提供详细迁移说明。
2. **通过代码库原生的工具链重新生成 Lockfile 依赖锁文件**（`npm install pkg@ver`、`uv lock`、`poetry update pkg` 等）——**绝对严禁手工修改锁文件**。
3. **在发起 PR 前进行实测验证**：全新安装依赖、执行构建编译、运行项目的自动化测试套件。测试失败变红 → 调查原因；若依赖升级本身破坏了构建，记录发生冲突纠缠的具体原因，并提议次小的替代升级路径，切勿霸王硬上弓强行升级。
4. **PR 正文结构规范**：列出解决的安全通告 ID、依赖包旧版本 → 新版本、源自审计的可达性研判结论（一句话）、以及实际运行的验证测试命令。跳过冗长的 CVE 样板废话——直接附上安全通告官方链接即可。
5. **将标记为 `accept-with-note`（接受风险）的安全通告排除在 PR 改动之外**；将其记录在 PR 正文中的“已知暂不修复清单”中并附带合理理由，确保决策公开透明且未来随时可复核。
6. **绝不要自行合并你自己的升级 PR**——交付它，并向审查者提示应重点核查哪些方面（通常包括：锁文件 Diff 的合理性以及测试套件的运行结果）。
