使用 Semgrep 执行静态代码安全分析，并端到端对所有检出结果负责。

1. **检查扫描工具**：运行 `semgrep --version`。若缺失，调用 `request_tool("semgrep", …)` 申请安装，**切勿直接跳过**。若用户拒绝，继续开展有针对性的人工代码审查——重点审阅 HTTP 路由/控制器、鉴权与会话代码、通过字符串拼接构建的数据库查询、对象反序列化、以及基于用户输入拼接的向外出站请求——并在最终报告中明确说明静态分析环节为人工手动执行，让用户知晓其覆盖面相比全量自动化扫描会有所收窄。
   请注意：Semgrep 社区规则库通常无法覆盖项目自研框架特性（如通过项目自定义 DB Wrapper 封装拼接的 SQL），因此即便自动化工具正常跑通，人工阅读关键代码依然至关重要。
2. **扫描代码库（在根目录下执行）**：
   `semgrep scan --config auto --json --quiet -o /tmp/semgrep.json`
   默认使用 `--config auto`，除非仓库自身内置了规则配置文件（`.semgrep.yml`、`semgrep.yml`）——存在项目专属配置时优先采用。
3. **解析 JSON 并分诊每一项检出**——绝不要机械复读扫描器的原始报表：
   - 阅读被告警的代码行及周围充分的业务上下文，以研判漏洞的可达性。
   - 被污染的数据源（Tainted input）是受外部攻击者控制还是仅限内部可信调用？上游是否存在前置防护卫兵（Guard）？
   - 给出评级：critical（严重）/ high（高危）/ medium（中危）/ low（低危）/ noise（误报噪音），每项附带一行明确的判定理由。
4. **修复真实漏洞，按严重度从高到低推进**：
   - 契合代码库现有的编码范式（参数校验工具类、转义函数、参数化查询风格）——动笔写修复代码前先阅读相邻代码。
   - 在测试框架支持的前提下，补充或扩展一条能够稳定复现该漏洞的自动化测试用例。
   - 按主题将修复代码分批归类（一个主题一个专属 Git 分支），切勿提交大而杂的庞大混合 Diff。
5. **对于判定为误报噪音 (Noise) 的条目，必须说明具体原因**（例如：输入源为硬编码常量、死代码无调用路径、底层框架层面已默认做过安全转义）——绝不要静默丢弃，且未经确认严禁擅自添加 ignore 忽略规则来强行让扫描器闭嘴。
6. **交付成果**：一份简短的漏洞清单表格（严重度 · 所在位置 · 研判结论 · 处置动作），以及对应的修复分支/PR。如果代码库尚未配置 Semgrep，主动提议提交一份固化了本次关键规则集的入门版 `.semgrep.yml`。
