name: security-fix-pr
description: 将分诊后的安全漏洞转化为聚焦、清晰可审查的代码修复 PR
---
[English](SKILL.md) · [简体中文](SKILL_cn.md)

将安全修复方案规范打包，确保繁忙的代码审查者能够信心十足地快速批准合并。

1. **按单一主题组织 PR**（例如“对报表模块中的 SQL 执行参数化绑定”），**绝不要将多种无关安全修改混杂打包**。小巧聚焦的 Diff 容易被快速 Review；庞大混杂的 Diff 只会被无限拖延搁置。
2. **分支命名规范**：从仓库的默认分支切出 `security/<theme>`。严格遵循代码库原有的 Git Commit 提交信息风格。
3. **每个修复 Commit 必须携带对应测试**：在代码库原有的测试布局和习惯下，补充或扩充一条若没有该修复就会直接报错失败的测试用例。若因客观原因无法编写自动化测试，在 PR 描述中坦诚说明，切勿静默忽略。
4. **PR 正文结构规范（保持紧凑精炼）**：
   - 漏洞问题说明：用平实易懂的人话讲清漏洞严重级别，以及为什么在该特定业务场景下很关键（一两句话说明可达性与危害影响，拒绝扫描器的假大空模版套话）。
   - 修复动作说明：修复了什么，以及本次改动**特意未触碰**哪些范围。
   - 验证方式：如何核验的（具体的测试函数名、实际执行的验证命令）。
   - **绝对严禁在公开 PR 中贴出明文凭证、Exploit 利用 Payload 或手把手的攻击复现步骤**——抽象描述漏洞类别即可。
5. 若 GitHub 连接器可用，直接调用接口创建 PR；若不可用，准备好本地分支并向用户提供精确的 `git push` 与创建 PR 的终端命令。
6. 编写修复归你，**代码合并 (MERGING) 归人类团队**。**绝不要自行合并你自己的安全 PR**——提交它，并向审查者汇总提示应当重点审查哪些边界细节。
