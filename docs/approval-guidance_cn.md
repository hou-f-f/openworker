# 协作角色与团队的审批指导原则 (Approval Guidance)

[English](approval-guidance.md) · [简体中文](approval-guidance_cn.md)

角色 (Coworker) 的编写者可以在角色配置清单中独立于系统提示词（System Prompt），为自动审批审查者（Auto-approve Reviewer）提供一到两个段落的指导原则：

```yaml
approval_guidance: >-
  在获准授权的本地应用中独立验证所分配的验收标准。
  在分配的临时目录中安装项目本地的测试依赖和截取屏幕截图属于常规操作。
  未经用户显式授权覆盖，不得访问生产环境、发布修改或发送外部消息。
```

这个可选的 manifest 字段最多可容纳 2,400 个字符。它适用于工程研发、安全防护、内容产出等各类角色。应在此描述该角色的**常规合法工作范围**以及**明确的操作红线与边界**，切勿编写“盲目批准所有操作”的空泛指令。在多 Agent 团队中，Lead（主导者）角色的 manifest 还会为其管辖的 Workers 在接受审查时提供团队级全局指导。

团队 Lead 可以在 `propose_team.members[].approval_guidance` 中为各个成员提议额外的针对特定任务的指导文本。在界面的团队配置卡片中，该项收拢在折叠的 **高级设置 (Advanced)** 面板下，用户可以对每个 Worker 进行逐一编辑。在用户正式批准创建团队时，系统会将人类确认的准确文本持久化保存到团队花名册（Roster）中。清空该文本则保存为空白段落。若人类决策中省略了该项，绝不会自动继承 Lead 的建议。后续的对话引导（Steering）无法篡改该文本；当前版本不向 Agent 暴露任何修改此配置的操作。

Reviewer 审查者大模型在做审批裁决时，会接收当前 Coworker/团队的定义、经人类核准的 Worker 指导段落、实际分配的任务与验收标准、授权工作目录、可用连接器、权限运行模式以及已保存的用户自定义规则。委托执行的审批必须还原为原始 Worker 所请求调用的具体工具及参数，绝不会把 Lead 的推荐意见直接当成权限放行。

来自项目所有者（人类用户）的直接消息会保持原始传递，不经过二次语义抽取或单条消息截断。带有来源标签的看板唤醒（Board Wakes）、连接器事件推送以及 Agent 之间的消息传递**不属于**人类直接消息。来源不明的 Worker 输入会被单独标注；历史上的 Agent 引导记录不能被认证为人类授权。如果序列化后的请求/历史/上下文整体超过 64,000 个字符，系统将直接判定为存在不确定性并升级上报给人类，绝不进行静默截断。上下文环境发生任何变更都会导致正在进行的审查结果直接失效。

指导原则（Guidance）仅作为辅助大模型做出安全推理判断的参考依据。它**绝不能**直接赋予任何连接器或工具访问权限，**绝不能**绕过硬性安全底线（Hard Permission Floors），也**绝不能**覆盖用户显式配置的限制。任务分配文本与 Lead 的口头声称并不构成关于凭证或临时基础设施的已验证事实。Reviewer 并不会逐行分析引用的未知脚本内容或环境配置文件，因此对于不透明的脚本执行操作，仍可能要求人类介入确认。
